#+title: Hactar Big Refactor Plan — Hactar IS the Project CLI
#+author: k
#+startup: overview

* The Reimagined Core Idea

Hactar is not a tool you point at a project. *Hactar becomes the project.*

On first run in a repository, Hactar generates a version of itself specialized
to that project and its stack — written out as =.hactar.lisp=. From then on,
"running Hactar" means running *that file*. The generic engine recedes into a
library; the project's =.hactar.lisp= is the application.

Inside Hactar, an agent watches what you (and other agents) actually do, and
uses a fast *diffusion model* to continuously rewrite =.hactar.lisp= — adding
verbs, refining prompts, learning the stack — then reloads itself. The CLI
literally grows into the shape of the work.

#+begin_quote
Hactar is a DSL for building dev tooling from LLMs. =.hactar.lisp= is a program
written in that DSL — and Hactar writes (most of) it for you, then keeps
writing it.
#+end_quote

Three things make this real, and each is a section below:

1. *Self-generation* — first run extracts the project and emits =.hactar.lisp=.
2. *Self-update* — a self-update agent (=--auto-update=, default on) monitors chat
   history + tool calls on every turn using a hook, and diffuses edits into
   =.hactar.lisp=, where the agent is allowed to emit any Lisp code.
3. *Self-hosting* — the build always lands at =./hactar/build/hactar=, and a
   generated =.envrc= + a global launcher shim make =hactar= resolve to the
   project's own binary.

The good news: the spine for all three already exists in the codebase
(=project-cli.lisp=, =lisp-form-parser.lisp=, =diffusion-complete=). The one
piece we *rebuild rather than reuse* is the synthesis pipeline: the existing
=fusion.lisp=/=deffusion= macro is replaced by a handful of small functions.
This refactor *promotes that spine to the center* and deletes everything that
competes with it.

* Inspiration: Flue — Hactar Generates the Harness, Not Just Verbs

[[https://flueframework.com][Flue]] is a TypeScript framework where you *define an
agent by composing a harness*: a model, a set of tools, a set of skills, a
sandbox, and instructions — then run it anywhere. Its core form is data:

#+begin_src typescript
export default defineAgent(() => ({
  model:   'anthropic/claude-sonnet-4-6',
  tools:   [replyToIssue],          // typed functions the agent may call
  skills:  [triage, verify],        // SKILL.md capability bundles
  sandbox: local(),                 // virtual / local / remote container
  instructions,                     // the agent's standing brief
}));
#+end_src

The idea we steal: *the unit of generation is a composed harness, not a loose
verb*. Today Hactar already has the pieces — =defagent= (=agents.lisp:23=),
=defmode= with =defmode-command= scaffolds (=react-router.lisp:20-58=), tools
(=tools.lisp=), skills (=skills-mode.lisp=), and sandboxes
(=sandbox.shell.nix=) — but they are hand-written per stack. The reframing:

#+begin_quote
Hactar is a *library* for synthesizing a bespoke agent + harness for one project.
=.hactar.lisp= is the generated harness — a Flue-style =defagent= composed from
=tool=, =skill=, =sandbox=, =prompt=, and stack-specific =action= forms — and
Hactar writes (most of) it for you, then keeps writing it.
#+end_src

So self-generation does not stop at =defroutes=/=defmodels=. From the detected
stack it emits a *project-tailored harness*: the agents, the tools they may call,
the skills they load, the sandbox they run in, and the =defaction= verbs that
scaffold *that stack's* artifacts. A TypeScript + React Router repo gets
TypeScript-aware tooling and verbs like =route.create= / =api.create=; a Rails
repo gets =migration.create= / =controller.create=; etc. (worked example below).

** Worked example — TypeScript + React Router

On first run in a TS + react-router repo, Hactar detects the stack
(=react-router.lisp:6-17=) and diffuses a generated region that *composes a
harness specific to that project*:

#+begin_src lisp
;; ── BEGIN GENERATED (TypeScript + React Router) ──
(defproject :stack ("typescript" "react" "react-router" "vite"))

;; Tools: typed, sandboxed functions the agent may call (Flue `tools:`)
(deftool tsc       :run "npx tsc --noEmit"           :doc "Type-check the project.")
(deftool vitest    :run "npx vitest run {{args}}"    :doc "Run unit tests.")
(deftool rr-routes :run "npx react-router routes"    :doc "List the route tree.")

;; Skills: capability bundles loaded into context (Flue `skills:`)
(defskill react-router :doc "react-router.org" :rules :react-router)

;; Sandbox the harness runs in (Flue `sandbox:`)
(defsandbox project :kind :local :allow ("npx" "node" "git"))

;; Actions: stack-specific scaffolding verbs (route+prompt+apply)
(defaction route.create
  :doc    "Create a typed React Router route + loader/action."
  :prompt "Create a React Router route {{name}} under src/routes using a typed
           loader and action, then register it in src/routes.tsx. {{doc:react-router}}"
  :apply  :create)

(defaction api.create
  :doc    "Create a typed API resource route (server loader/action)."
  :prompt "Create an API resource route {{name}} with typed request/response
           handlers for this {{stack}} project. {{doc:react-router}}"
  :apply  :create)

;; Agent: the composed harness (Flue `defineAgent`)
(defagent dev
  :model    "anthropic/claude-sonnet-4-6"
  :tools    (tsc vitest rr-routes)
  :skills   (react-router)
  :sandbox  project
  :instructions "Build React Router features end-to-end: scaffold the route,
                 wire data loaders/actions, type-check, and verify with vitest.")
;; ── END GENERATED ──
#+end_src

Running =hactar route.create Dashboard= dispatches the generated =defaction=;
=hactar dev "add a settings page"= runs the composed agent with its TS-aware
tools, react-router skill, and sandbox. The same harness can be run by =hactar=
locally or invoked headless in CI — "define once, run anywhere," the Flue
property, applied to per-project dev tooling.

* The Two-Layer Architecture

** Layer 1 — The Engine (a library: =hactar-core=)
The kernel + the self-gen/self-update machinery. Installed once, globally
(=ros install=, Nix, release tarball). Provides the DSL, the dispatcher, the
LLM/diffusion clients, the builder, and the watcher. It defines *no project
verbs of its own* beyond bootstrap (=init=, =update=, =build=, =doctor=).

** Layer 2 — The Project (=.hactar.lisp=: the application)
A single per-repo file that =(in-package :hactar)= and is *pure composition of
kernel primitives*: =defproject=, =defmodels=, =defroutes= (data); =defmode=,
=defaction=, =defprompt=, =defdoc= (behavior); and the Flue-style *harness*
forms =deftool=, =defskill=, =defsandbox=, =defagent= (a composed agent). It has
two regions, already established by the writer (=lisp-form-parser.lisp:207-222=):

- =;; BEGIN GENERATED= … =;; END GENERATED= — owned by the generator + the
  self-update agent; freely rewritten.
- A *user region* — hand edits the agent must preserve
  (=pcli-extract-user-region=).

Loading =.hactar.lisp= builds the in-memory model and registers the project's
verbs. *That file is the CLI.*

#+begin_src text
   ┌─────────────────────────────────────────────┐
   │ hactar-core  (global library / engine)       │
   │   kernel primitives · diffusion · builder ·  │
   │   watcher · bootstrap verbs (init/update)    │
   └───────────────────────┬─────────────────────┘
                           │ (require + compose)
   ┌───────────────────────▼─────────────────────┐
   │ ./.hactar.lisp  (per-project application)    │
   │   defproject/defmodels/defroutes  (DATA)     │
   │   defmode/defaction/defprompt/defdoc (BEHAV) │
   │   deftool/defskill/defsandbox/defagent (HARNESS) │
   │   ── BEGIN GENERATED … END GENERATED ──      │
   │   ── user region (preserved) ──              │
   └──────────────────────────────────────────────┘
            compiled to → ./hactar/build/hactar
#+end_src

* Lifecycle

#+begin_src text
 first run            every run             during a session (opt-in)
 ─────────            ─────────             ──────────────────────────
 detect stack         load .hactar.lisp     watch chat + tool calls
 extract map          dispatch verb   ◄──┐  └─► diffuse edits to .hactar.lisp
 diffuse behavior     run               │      validate (closed API)
 emit .hactar.lisp                      │      hot-reload (or rebuild)
 build binary                           └──────────── reload ───────────┘
 write .envrc
#+end_src

- *Bootstrap* (no =.hactar.lisp= present) → generate + build + wire =.envrc=.
- *Run* → the project binary loads =.hactar.lisp= and dispatches.
- *Self-update* (when enabled) → the watcher feeds activity to the diffusion
  agent, which rewrites the generated region and reloads.

* The Kernel = The Surface (one vocabulary, two audiences)

The kernel is a *small set of orthogonal primitives*. Crucially, the same macros
serve **two audiences**: a human hand-editing =.hactar.lisp=, and the diffusion
agent emitting forms. The set of forms the agent may emit is exactly this set —
the **Surface** (see "API subset" below).

| # | Primitive   | One job                                        | Today's home        | Status        |
|---+-------------+------------------------------------------------+---------------------+---------------|
| 1 | =llm=       | talk to a model: =complete=/=ask=/=diffuse=    | llm.lisp, llm-utils | keep          |
| 2 | =prompt=    | named, templated text: =defprompt=             | prompts.lisp        | keep, extend  |
| 3 | =context=   | assemble prompt context (files/docs/rules)     | context.lisp        | keep, slim    |
| 4 | =route=     | input string -> handler: =defroute=/=defflag=  | router.lisp         | keep; unify   |
| 5 | =mode=      | the *module*: when+rules+prompts+actions       | mode.lisp           | keep; promote |
| 6 | =interface= | two-way file<->state (the org surface)         | interface.lisp      | keep; promote |
| 7 | =knowledge= | =$hypertext= docs/snippets by URI: =defdoc=    | hypertext.lisp      | keep, rename  |
| 8 | =project=   | the data map: =defproject/defroutes/defmodels= | project-cli.lisp    | keep; CENTER  |
| 9 | =tool=      | typed fn the agent may call: =deftool=         | tools.lisp          | keep; promote |
|10 | =skill=     | a capability bundle (SKILL.md): =defskill=     | skills-mode.lisp    | keep; promote |
|11 | =sandbox=   | where the harness runs: =defsandbox=           | sandbox.shell.nix   | add form      |
|12 | =agent=     | composed harness (model+tools+skills+sandbox+instructions): =defagent= | agents.lisp | keep; promote |

Primitives 9–12 are the *harness layer* (the Flue inspiration): =defagent= is the
=defineAgent= analog, composing =tool=/=skill=/=sandbox=/=prompt= into one runnable
unit. Like the rest, they are emittable by the diffusion agent and live on the
Surface.

Two engine-internal services that power self-update (not user-facing verbs):
- =synth= : a *new, small* synthesis pipeline (see "Self-Update Agent") — plain
  functions, not the old macro-heavy =deffusion=/=fusion= stack, which is
  *deleted and rebuilt*. Wraps =diffusion-complete= + =parse-diffusion-output= +
  the Surface validator.
- =builder=  : =asdf:make= a project binary to =./hactar/build/hactar=.

** The one composition that defines a verb: =defaction=
=ACTION ≡ route + prompt + context → llm → apply=. A declarative verb whose body
is data — the form the diffusion agent most often writes.

#+begin_src lisp
(defaction add.auth
  :doc    "Add authentication to the project."
  :prompt "Add authentication to project for {{stack}} using {{doc:auth}}."
  :apply  :search-replace)
#+end_src

Bindings resolved from the kernel: ={{stack}}= (project =:stack=), ={{context}}=,
={{doc:NAME}}= (knowledge), ={{model:NAME}}=/={{route:NAME}}= (data map), and
route args. =:apply= ∈ {=:show=, =:search-replace=, =:create=, =:shell-confirm=,
=:none=}. Dots, most mode commands, and the old =mold-pour= all collapse into it.

* Self-Generation (first run)

Already 80% built: =generate-project-cli-file= (=project-cli.lisp:1027=) does
detect-stack → extract routes/models → =write-hactar-lisp= → =load=. The refactor
extends it from *data-only* to *data + behavior*, and replaces the
=run-active-fusions= call with a single =synth-update= pass (the rebuilt
pipeline; same one used by self-update).

** Pipeline
1. =ensure-repo-root= + =pcli-detect-stack= (existing analyzers).
2. Hard-coded extraction via plain =extract-*= functions (=extract-routes=,
   =extract-models=, scripts/deps/envs) → deterministic
   =defroutes=/=defmodels=/=defscripts=. (These absorb the old =:fern-extract=
   stage logic, decoupled from any pipeline macro.)
3. *Behavior + harness synthesis* (new): from the detected stack, select
   =defmode=s and emit a starter set of =defaction=s + =defprompt=s *and the
   project's harness* (=deftool=/=defskill=/=defsandbox=/=defagent=, the Flue
   inspiration) via one =synth-update= / =diffuse-forms= call constrained to the
   Surface (below), seeded by stack templates in =starters.lisp=/=preset.lisp=.
4. =write-hactar-lisp= with preserved user region (existing).
5. =builder=: =asdf:make= → =./hactar/build/hactar=; verify it loads
   (=check-string=/checker) before swapping in.
6. =doctor=: write =.envrc=, ensure =hactar/build/= is gitignored, print next
   steps.

** Entry points
- =hactar init= (existing =init= sub-command, extended): full bootstrap.
- =hactar scan= / =hactar project.update=: re-extract the generated region only.
- =hactar build=: (re)compile the project binary.

* Self-Update Agent (the diffusion loop)

The differentiator. *On by default.* Controlled by a flag/config key
=:auto-update= (=defflag :auto-update= + =config.lisp= persistence). The self-update
agent watches the session and continuously reshapes =.hactar.lisp=.

** What it watches (the signal)
Subscribe, via the existing =nhooks= hook system, to:
- *Chat history* — user/assistant turns (=history.lisp=, =session.lisp=).
- *Tool calls* — every tool invocation + result (=tools.lisp=, ACP/MCP events).
- *Applied edits* — search/replace results, created files, run commands.

These are the "diff signal": evidence of verbs the user keeps doing by hand,
docs they keep pulling, prompts they keep retyping — candidates to crystallize
into =defaction=/=defprompt=/=defdoc= forms.

** The loop (a new, small synthesis pipeline — NOT =deffusion=)

We *delete the existing =fusion.lisp=/=deffusion= machinery and rebuild it* as a
handful of plain functions. The old =deffusion= is a heavy code-generating macro
(=fusion.lisp:11-118=) that expands a five-keyword stage DSL
(=:fern-extract= / =:diff-detect= / =:diffuse= / =:validate= / =:emit=) into a
generated =run-fusion-NAME= function, with stage-variable plumbing, a fern
dependency baked into extraction, and a stub =:diff-detect=. It is more
machinery than the job needs and is hard for the agent (or a human) to reason
about.

Replace it with five ordinary functions wired by one tiny driver — no macro, no
DSL, no registry:

#+begin_src lisp
(defun synth-update (project &key (apply t))
  "One self-update tick. Returns the merged forms (or NIL if no change)."
  (let* ((signal  (collect-signal project))                 ; recent turns+tools
         (current (read-hactar-lisp (hactar-file project)))  ; existing forms
         (candidates (when (signal-ready-p signal current)   ; debounce/threshold
                       (diffuse-forms project signal current))))
    (when candidates
      (let ((valid (validate-forms candidates)))             ; closed Surface only
        (when valid
          (let ((merged (merge-hactar-forms current valid)))
            (when apply (apply-update project merged))        ; write + reload + guard
            merged))))))
#+end_src

The five helpers (each independently testable):
1. =collect-signal= — window + redact recent chat/tool/edit events (from hooks).
2. =diffuse-forms= — build the prompt (Surface spec + current file + signal),
   call =diffusion-complete=, =parse-diffusion-output= → candidate forms.
3. =validate-forms= — =validate-hactar-form= against the closed Surface +
   =correct-hactar-form=; drop anything off-Surface.
4. =merge-hactar-forms= — into the GENERATED region only (reused as-is from
   =lisp-form-parser.lisp=; the user region stays untouched).
5. =apply-update= — =write-hactar-lisp :merge-p t=, hot-=load=, and on
   =check=/load failure roll back to last-known-good.

What we *keep* from today (these are good, small, and already used):
=diffusion-complete=, =parse-diffusion-output=, =read-hactar-lisp=,
=merge-hactar-forms=, =write-hactar-lisp=, =validate-hactar-form=. What we
*drop*: the =deffusion= macro, =*fusion-registry*=, the =fusion= struct,
=run-active-fusions=, the stage-keyword DSL, and the =fusions/*= files. Hard-coded
structural extraction (the old =:fern-extract= stage) moves to plain
=extract-*= functions used during *generation* (Self-Generation), not the update
loop — keeping the update loop pure signal→forms with no parser dependency.

#+begin_src text
collect-signal            ; recent turns + tool calls (windowed, redacted)
   │
signal-ready-p            ; debounce / threshold vs current .hactar.lisp model
   │  (driven by a hook on each turn)
diffuse-forms             ; diffusion-complete( surface-spec + current-file + signal )
   │                        → candidate Hactar forms (parse-diffusion-output)
validate-forms            ; validate-hactar-form against the closed Surface;
   │                        correct-hactar-form heuristics; reject anything else
merge-hactar-forms        ; into GENERATED region only (user region untouched)
   │
apply-update              ; write-hactar-lisp :merge-p t; load (hot); rollback guard
#+end_src

** Cadence & safety
- *Hot-reload by default*: =load= the merged file into the running image (sub-second);
  only =builder= rebuilds the binary on session end or on =hactar build=.
- *Human-in-the-loop modes*: =:auto-update= ∈ {=nil=, =:suggest= (write to an
  inbox / show a diff), =:auto= (apply silently)}. Default is =:auto= (auto-update).
- *Rollback*: keep the last-known-good =.hactar.lisp= (and binary); revert if the
  new file fails =check-string= or fails to load.
- *Loop guard*: never let an update triggered by an update trigger another;
  rate-limit; ignore the agent's own edits in the signal.

* The API Subset Passed to the Diffusion Model (the "Surface Spec")

The diffusion model must only ever produce forms Hactar can safely load. This is
already modeled by =*hactar-form-schemas*= (=lisp-form-parser.lisp:3-13=) — a
whitelist with required/optional keys per form, enforced by =validate-hactar-form=
with =correct-hactar-form= heuristics. The refactor:

1. *Extend the schema* from data-only to include behavior + harness forms:
   =defmode=, =defaction=, =defprompt=, =defdoc=, =defroute=, and the harness
   forms =deftool=, =defskill=, =defsandbox=, =defagent=. Each gets a
   required/optional key spec (e.g. =defaction= → required =(:doc)=, one of
   =(:prompt :prompt-file)=, optional =(:apply :when)=; =defagent= → required
   =(:model)=, optional =(:tools :skills :sandbox :instructions)=).
2. *Generate the spec to feed the model* from the schema, reusing the existing
   spec machinery (=build-subcommand-group-spec=, =--spec-lisp=/=--spec= in
   =hactar.lisp:2417-2422=). The diffusion system prompt embeds:
   - the Surface grammar (allowed forms + keys),
   - the current =.hactar.lisp= (or just its generated region),
   - a compact view of the project model (stack, routes, models),
   - the activity signal.
3. *Flexible scope*: the agent is not restricted to high-level primitives like
   =defaction=/=defmode=; it can emit raw =defroute=, =defflag=, or any arbitrary
   Lisp code.
4. The Surface Spec is the single source of truth shared by: the diffusion
   prompt, the validator, =--spec= output for editors, and the docs.

* Self-Hosting: Binary & Symlink Strategy

Goal: =hactar= in a project shell always means *that project's specialized
binary*, with zero manual symlinking, on machines with or without direnv.

** Canonical build path
All project builds output to a stable, gitignored path:
=./hactar/build/hactar=. =builder= (=asdf:make=, via the Makefile =build= target)
writes here; =init=/=build= ensure =hactar/build/= is in =.gitignore=.

** Primary: generated =.envrc= (direnv)
=doctor= writes (and offers to commit) a minimal =.envrc=:
#+begin_src sh
# .hactar — managed by Hactar
PATH_add hactar/build      # `hactar` now resolves to ./hactar/build/hactar
watch_file .hactar.lisp    # re-enter env when the CLI changes
#+end_src
=PATH_add= (not an alias) means =hactar <verb>= transparently runs the project
binary. =.envrc= is safe to commit; =hactar/build/= is not.

** Fallback: the global launcher shim (no direnv required)
The globally-installed =hactar= becomes a *thin launcher*:
1. If =./hactar/build/hactar= exists and is current (newer than =.hactar.lisp=),
   =exec= it with the same args.
2. If =.hactar.lisp= is newer, rebuild first (or hot-load if running a session).
3. If neither exists, run bootstrap (=init=).

This guarantees correct behavior even without direnv, on Windows, or in CI —
the global binary self-delegates to the project binary. direnv just removes the
indirection.

** Dev vs release
- *Dev / self-update*: a resident core image + =load .hactar.lisp= → instant
  reload, no per-turn compile.
- *Release*: =asdf:make= a standalone =./hactar/build/hactar= for fast cold
  starts and distribution. The launcher prefers the binary when present.

* How the Original Simplification Goals Fold In

The self-generating frame *requires* the same cleanups — a small, closed,
composable kernel is what makes a diffusion model able to write the CLI safely.

| Original goal                          | Now justified by                                                                                                                         |
|----------------------------------------+------------------------------------------------------------------------------------------------------------------------------------------|
| Dots = routing + prompts (=defaction=) | Actions are the agent's primary output form; dots' bespoke registry can't be diffused safely. Delete =dots.lisp=.                        |
| Remove molds                           | Molds are a second schema competing with =defproject/defmodels=. One project model is what the agent edits. Delete =molds.lisp=.         |
| Modes are THE module                   | Modes are the unit the generator selects per stack; behavior synthesis emits modes + actions.                                            |
| One org interface (litmode+monolith)   | =.hactar.org= becomes the *human-facing two-way view* of the same project model (=definterface :format :org=); litmode/monolith deleted. |
| Massive DSL simplification             | The kernel *is* the Surface the diffusion model writes. A small closed vocabulary is a safety requirement, not just aesthetics.          |

(Per-goal mechanics — =defaction= expansion, mold→data-map migration, mode
boilerplate factoring, the =:hactar= aggregate org interface — are unchanged from
the prior plan and still apply.)

* Phased Migration

Each phase compiles, passes =make test=, and is independently shippable.

** Phase 0 — Safety net
Characterize current behavior: project-cli generate/load round-trip, form
validation/merge, a representative dot, a mode scaffold. These become the
regression oracle for self-modification.

** Phase 1 — Engine/app split
Carve =hactar-core= out of =hactar.asd= (kernel + diffusion + builder). =.hactar.lisp=
becomes the application that composes it. Prove =hactar= still runs by loading a
trivial generated file.

** Phase 2 — =defaction= + harness forms + extend the Surface schema
Add =defaction= (route+prompt+apply) and the Flue-style harness forms
=deftool=/=defskill=/=defsandbox=/=defagent= (composing model+tools+skills+
sandbox+instructions). Extend =*hactar-form-schemas*= with
=defaction/defmode/defprompt/defdoc= and =deftool/defskill/defsandbox/defagent=.
Generate the Surface Spec from the schema.

** Phase 3 — Self-generation of behavior + harness
Extend =generate-project-cli-file= to emit modes/actions/prompts *and the
project-tailored harness* (tools/skills/sandbox/agent) — e.g. the TS +
react-router worked example above — not just data. Replace =run-active-fusions=
with a single =synth-update= pass. Validate generated files load + pass checks.

** Phase 4 — Builder + self-hosting
=builder= target → =./hactar/build/hactar=. Generated =.envrc= + global launcher
shim + =.gitignore= wiring. Verify =hactar <verb>= resolves to the project binary
with and without direnv.

** Phase 5 — Rebuild the synthesis pipeline + self-update agent
*Delete* =fusion.lisp= (the =deffusion= macro, =fusion= struct, =*fusion-registry*=,
=run-active-fusions=) and the =fusions/*= files. Build the new =synth-*= functions
(=collect-signal=, =diffuse-forms=, =validate-forms=, =apply-update=, driver
=synth-update=). Wire the watcher (hooks on history + tool calls) → =synth-update=
→ validate → merge into GENERATED region → hot-reload. Implement =:auto-update= ∈
{=nil=,=:suggest=,=:auto=}, rollback, loop guard. Default is =:auto=.

** Phase 6 — Delete the competitors
Remove =dots=, =molds=, =litmode=, =monolith=, =org-mode=. Rewrite =*-mode.lisp=
as =defmode= + prompt folders. Build the =:hactar= org interface.

** Phase 7 — Extract & document
Split =codegen=/=fern= plug-in boundary; extract =ruhe=/=hyperfractal=.
Rewrite docs around: "Hactar generates a CLI for your project, then keeps
writing it."

* Risks & Safety (self-modifying software)

1. *Arbitrary code execution* — the model never emits free Lisp; only Surface
   forms, validated before load. The primitives are the sandbox.
2. *Bad rewrite bricks the CLI* — last-known-good file + binary kept; revert on
   =check=/load failure; =hactar doctor --reset= regenerates from scratch.
3. *Runaway loops* — debounce the signal; ignore the agent's own edits;
   rate-limit; updates can't trigger updates.
4. *Clobbering human edits* — only the GENERATED region is rewritten; the user
   region is extracted and preserved (existing =write-hactar-lisp= behavior).
5. *Privacy* — chat/tool signal is processed locally for the diffusion prompt;
   redact secrets; respect the same data boundaries as the rest of Hactar;
   =:auto-update= is off by default and explicit.
6. *Reproducibility* — =.hactar.lisp= is committed and diffable; every self-edit
   is a reviewable change in version control, not hidden state.

* Resolved Design Decisions

1. *Single Source of Truth*: =.hactar.lisp= is the one source of truth (holding
   both data + behavior). We do not keep a separate =.hactar.org= that tangles
   to it.
2. *Binary and Image*: Both will be shipped. We use the binary for distribution/release
   and the resident core image for interactive self-update sessions.
3. *Default Auto-Update*: The system defaults to auto-update enabled (defaulting to
   =:auto=).
4. *Watch Signal Granularity*: The watch signal is triggered on every turn using a
   hook.
5. *Agent Emission Scope*: The agent is not restricted; it can emit anything (including
   raw =defroute=/=defflag= or any Lisp code).
6. *Binary Rebuild Strategy*: The hactar binary is rebuilt locally in user projects.
   We distribute a version of hactar globally, which users install via Roswell. The
   included SBCL in hactar allows them to generate their new per-project hactar build.
   The binary is gitignored and not committed.

#+title: Library Divide Plan
#+author: k
#+startup: overview
#+begin_quote
A framework is a program you live inside. A library is a function you call.
Hactar is a composition of small libraries with data at the boundaries —
the engine is just the composition point.
#+end_quote

* Task Status

Current Phase: Phase 0 (charter)

* Philosophy

Think like a Clojure dev shipping to Clojars, not like a framework author.
Every boundary decision below follows from these rules:

1. *Libraries are functions over data.* Each library takes plain data
   (strings, plists, structs) and returns plain data. Effects (network,
   filesystem, subprocess) live at the edges and are swappable.
2. *Composition over integration.* A library never knows who composes it.
   =hactar-core= composes the libraries; no library depends back on the
   engine. (Ring handlers don't know about web frameworks.)
3. *Protocols at the seams.* Where behavior must vary, expose a special
   variable or generic function, not a conditional. Precedent:
   =*llm-client*= (mock vs live), =render-result=, the interface protocol.
4. *Small, closed surfaces.* One package per library; the export list *is*
   the API, exactly like a Clojure =ns= with a small public var set.
   =src/rebuild/packages.lisp= is the model.
5. *Accretion, not breakage.* Grow a library's surface; never change the
   semantics of an exported symbol. If semantics must change, add a new name.
6. *Independently loadable, independently useful, independently testable.*
   Every system must pass =make test-libs= in a fresh image, and each should
   be worth using from a bare REPL without the rest of Hactar.
7. *Mock-first effects.* Every effectful library ships an offline
   deterministic mock as its default test client (the =hactar-llm= precedent).
   =make test= never needs network or API keys.
8. *Data as libraries.* Stack knowledge (modes, prompts, rules, starters,
   wiki entries) is content, not code. Content packs are libraries of DSL
   forms/data that any engine version can load — like EDN-heavy Clojure libs.

* Current State

Two generations coexist:

- *The rebuild* (the keeper): =src/rebuild/= is =hactar-core= (~2.2k lines),
  already composed from five split libraries that load independently:
  =hactar-llm= (=src/llm/=), =hactar-org= (=src/org/=), =hactar-md=
  (=src/md/=), =hactar-fzf= (=src/fzf/=), =hactar-fern= (=src/fern/=).
  =hactar.asd= is a thin executable over =hactar-core=.
- *The legacy monolith* (the quarry): ~100 root =*.lisp= files (~39k lines),
  all in one =:hactar= package, per =RebuildHactarPlan.org= treated as
  "source material, not implementation to preserve wholesale".

Existing satellite systems already prove the library story: =hactar-codegen=,
=hactarsh=, =ruhe=, =hyperfractal=, plus the legacy =llm= system that
=hactar-llm= supersedes.

Problems this plan fixes:

1. The monolith's capabilities (TUI, ACP, MCP, OAuth, knowledge, watchers,
   sessions) have no home in the rebuild yet. Porting them into
   =hactar-core= would recreate the monolith.
2. =hactar-codegen= depends on =hactar-core= — a plugin pointing up at its
   host. Dependency direction must be inverted.
3. ACP, MCP, lisp-rpc, and LSP each hand-roll the same JSON-RPC/stdio
   plumbing.
4. Mode/stack content is compiled into the engine instead of being
   loadable data.

* Dependency Rules

#+begin_src text
Tier 5  programs        hactar, hactarsh, ruhe, hyperfractal
Tier 4  content packs   hactar-modes-*, hactar-starters, hactar-wiki
Tier 3  adapters        hactar-acp, hactar-mcp, hactar-http, hactar-proxy,
                        hactar-knowledge, hactar-codegen*
Tier 2  engine          hactar-core
Tier 1  effectful       hactar-llm, hactar-jsonrpc, hactar-vfs,
        primitives      hactar-watch, hactar-sandbox, hactar-tui
Tier 0  pure data/text  hactar-fzf, hactar-md, hactar-org, hactar-fern

(*hactar-codegen sits at Tier 3 for packaging but must depend only on
 Tier 0/1 — see its charter.)
#+end_src

Rules:

1. Dependencies point strictly downward. No cycles, no same-tier deps
   except where a charter says so explicitly (e.g. =hactar-tui= → =hactar-md=).
2. Tier 0 depends only on the blessed external base (=uiop=, =str=,
   =cl-ppcre=). No sockets, no subprocesses.
3. =hactar-core= composes Tiers 0–1 and defines the protocols Tiers 3–4
   implement. It must never name an adapter or content pack.
4. Adapters translate between an external protocol and the core dispatcher/
   result model. They own their transports.
5. Content packs contain only closed-surface DSL forms and data. Loading
   one registers content; it computes nothing at load time.
6. Programs are thin: parse argv, compose systems, call =dispatch=.

** Tier 1: Effectful primitives

*** =hactar-llm= (exists — grows by accretion)

The one provider-agnostic LLM boundary. Everything that talks to a model
API lives here and nowhere else.

- Source :: =src/llm/= (done: mock + protocol). Quarry legacy =llm.lisp=
  (provider clients, streaming), =models.lisp= (model registry),
  =llm-utils.lisp= (=diffusion-complete=), =api-complete.lisp= (completion
  API), =oauth.lisp= (device/PKCE subscription flows), =copilot.lisp=
  (GitHub Copilot API). Legacy =llm.asd= system is retired when parity lands.
- Deps :: =dexador=, =shasht=, =flexi-streams=, =babel= (live client only —
  keep the mock path dependency-free so Tier 0 test images stay light).
- Surface :: =*llm-client*=, =llm-chat=, =llm-stream=, =diffusion-complete=,
  =embed=, =list-models=, =resolve-model=, =oauth-login=, =token-count=,
  =*mock-llm-output*=, =*mock-diffusion-output*=.
- Note :: OAuth is here because a credential is an LLM-provider concern;
  it exports data (tokens), not commands.

*** =hactar-jsonrpc= (new)

JSON-RPC 2.0 framing over stdio/socket streams. Extracted once, used by
ACP, MCP, lisp-rpc, and LSP instead of four hand-rolled copies.

- Source :: the duplicated plumbing in =acp.lisp=, =mcp.lisp=,
  =lisp-rpc-protocol.lisp=, =lsp.lisp=.
- Deps :: =shasht=.
- Surface :: =make-server=, =register-method=, =serve=, =notify=,
  =make-client=, =call=, =rpc-error=, Content-Length framing helpers.
- Test :: pure in-memory streams; no process needed.

*** =hactar-vfs= (new)

Virtual/staged filesystem: plan writes as data, inspect the plan, then
commit. The write-side twin of =hactar-fern='s read side.

- Source :: =vfs.lisp=.
- Deps :: =uiop=.
- Surface :: =make-vfs=, =vfs-write=, =vfs-read=, =vfs-diff=, =vfs-plan=,
  =vfs-commit!=, =with-staged-fs=.
- Used by :: =hactar-codegen= (emit targets), =hactar-core=
  (generated-region rewrites become inspectable plans).

*** =hactar-watch= (new)

Filesystem event watching (the cl-fs-watcher adaptation), decoupled from
what reacts to events.

- Source :: =watchers.lisp= (652 lines) — keep the watcher, drop the
  built-in reactions; reactions are handlers the caller registers.
- Deps :: platform notify backend (as today).
- Surface :: =watch=, =unwatch=, =on-change= (callback registry),
  =pending-events=.
- Used by :: the self-update signal collector in =hactar-core=; editor
  adapters.

*** =hactar-sandbox= (new)

Sandbox policy as data + enforcement as a wrapper. Permissions and
allowlists in one place.

- Source :: =permissions.lisp= (484 lines), the =defsandbox= runtime
  checks in =src/rebuild/runners.lisp=, =sandbox.shell.nix= conventions.
- Deps :: =uiop= (subprocess launch).
- Surface :: =make-policy=, =policy-allows-p=, =with-sandbox=,
  =sandbox-exec=, =explain-denial=.
- Note :: =hactar-core='s =defsandbox= DSL form compiles to this library's
  policy data; the DSL stays in core, the mechanism lives here.

*** =hactar-tui= (new)

Terminal interaction toolkit: themes, prompts, spinners, hydras,
interactive selection, readline loop. Strictly presentation — it renders
=result= data and forwards input lines; it never dispatches.

- Source :: =tui.lisp= (2036), =tui-theme.lisp= (931), =hydra.lisp= (315),
  interactive half of =fzf.lisp=, terminal glue from =md-render.lisp=.
- Deps :: =hactar-md=, =hactar-fzf=, =cl-readline=.
- Surface :: =with-tui=, =read-input=, =render=, =theme=, =define-hydra=,
  =pick= (interactive select), =spinner=.
- Test :: render to string streams; golden-text tests, no tty required.

** Tier 2: The engine

*** =hactar-core= (exists — stays small)

The composition point: closed DSL surface, registries, state, hooks,
result model, route dispatch, bootstrap, generated-file read/write/preserve,
self-update loop, mode/interface protocols.

- Source :: =src/rebuild/= as-is; quarry =synth.lisp= +
  =diffusion-prompts.lisp= (self-update synthesis), =session.lisp= +
  =history.lisp= + =persist.lisp= + =context.lisp= + =preset.lisp= (session/
  context state — kept in core because they are the engine's own state, per
  Invariant 7), =assistant.lisp= (chat-turn loop), =check.lisp= (doctor).
- Deps :: Tier 0 + =hactar-llm=, =hactar-sandbox=, =hactar-vfs=
  (=hactar-watch= optional, loaded when self-update watching is on).
- Surface :: unchanged — the closed DSL surface exported for =hactar-user=
  (=defproject=, =deftool=, =defagent=, =defaction=, =defroute=, =generated=,
  ...), plus the runtime protocol (=dispatch=, =render-result=,
  =register-stack-mode=, interface protocol).
- Invariant :: core never gains a dependency on an adapter, a content
  pack, or =hactar-tui=. The default readline UI moves behind the interface
  protocol; a =--plain= core still works with no TUI loaded.

** Tier 4: Content packs (data as libraries)

One system per stack/domain; each is a pile of closed-surface DSL forms
and data files that =defmode= registers. No load-time computation. The
engine version they target is checked by the validator, not by ASDF.

- =hactar-modes-web= :: =react-mode.lisp=, =react-router.lisp=,
  =redwood-mode.lisp=, =js-mode.lisp= + related starters/prompts.
- =hactar-modes-ruby= :: =sinatra-mode.lisp=, Rails (=modes/rails.lisp=),
  Ruby starters (Roadmap Q1).
- =hactar-modes-shell= :: =sh-mode.lisp=, =agentshell-mode.lisp=.
- =hactar-modes-lisp= :: =lisp-mode.lisp=, =hactar-mode.lisp= (Hactar
  developing Hactar).
- =hactar-modes-services= :: =stripe-mode.lisp=, =gpt-mode.lisp=,
  =skills-mode.lisp= (Claude skills, Roadmap Q1), =npm.lisp=, =github.lisp=.
- =hactar-starters= :: =starters.lisp=, =create.lisp= data.
- Shared mode *machinery* (detect/extract/generate) stays in
  =hactar-core=; packs contain only registrations and content. =rules.lisp=
  and =prompts.lisp= registries are already core surface; pack files only
  add entries.

** Tier 5: Programs

- =hactar= (exists) :: the executable; composes core + chosen adapters +
  default packs; flags pick the interface (=--acp= loads =hactar-acp=,
  plain TTY loads =hactar-tui=, =--in-editor= loads neither).
- =hactarsh= (exists) :: readline shell on =hactar-tui= + core.
- =ruhe= (exists) :: webfeed generator; downstream proof of the library
  story.
- =hyperfractal= (exists) :: plaintext browser wrapper; ditto.
- =hactar-pro= (new, from =pro.lisp=) :: paid content-repo client;
  optional, never required by core.

* Deliberate Non-Splits

Restraint is part of the philosophy — a library must earn its =.asd=:

- =result.lisp=, =state.lisp=, =hooks.lisp= (rebuild versions) stay in
  =hactar-core=. A 28-line result struct is a contract, not a library;
  splitting it creates version-skew risk with zero reuse payoff.
- Route parsing stays in core; it is the engine's grammar.
- =config.lisp= / =debug.lisp= / =check.lisp= fold into core (doctor).
- =git.lisp= (30 lines of git utils) folds into core utils; it does not
  justify a system until someone needs it without Hactar.
- =slynk.lisp=, =dev.lisp= remain dev-image conveniences, not systems.

* Repository Layout

Monorepo, one directory per library under =src/=, one =.asd= per system at
the root (the established convention). Polyrepo is explicitly rejected for
now: shared CI, atomic cross-library refactors, and =make test-libs=
already give the isolation we want without release coordination overhead.

#+begin_src text
.
|-- Makefile
|-- hactar.asd  hactar-core.asd  hactar-llm.asd  hactar-org.asd ...
|-- src/
|   |-- core/        (rename of src/rebuild/ once legacy roots are gone)
|   |-- llm/  org/  md/  fzf/  fern/
|   |-- jsonrpc/  vfs/  watch/  sandbox/  tui/
|   |-- acp/  mcp/  http/  proxy/  codegen/  knowledge/  rag/
|   `-- packs/
|       |-- modes-web/  modes-ruby/  modes-shell/  modes-lisp/
|       |-- modes-services/  starters/
`-- tests/
    |-- core/  llm/  jsonrpc/  tui/  ...   (one suite per system)
#+end_src

Every library keeps the two-file minimum shape until it earns more:
=packages.lisp= (the surface) + =<name>.lisp= (the implementation).

* Testing Strategy

1. Extend =make test-libs= to iterate over every system in the graph;
   independent load in a fresh image is the merge gate.
2. Each library gets its own FiveAM suite mirroring
   =tests/rebuild/libraries.test.lisp=; suites run in dependency-tier
   order under =make test=.
3. Effectful libraries test against their mock protocol object
   (=*llm-client*= pattern); adapters test against in-memory streams
   (=hactar-jsonrpc= makes ACP/MCP testable without processes).
4. A =deps.test= asserts the dependency rules mechanically: walk ASDF
   system deps, fail on any upward or cross-tier edge.
